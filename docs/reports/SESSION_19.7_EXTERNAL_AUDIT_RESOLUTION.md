## 🔍 이슈 진단

### 발견된 거버넌스 모순

**모순 1: 세션 종료 프로토콜 vs PM 금지 권한**

```markdown
# CLAUDE.md 섹션 5 요구사항
세션 종료 전 반드시 수행:
1. 04_CURRENT_STATE.md 갱신 — 완료/진행중/이슈 업데이트

# CLAUDE.md 섹션 7.1 PM 금지 권한
- ❌ 정본 문서 직접 수정 (`CLAUDE.md`, `01~05` 금지)
```

→ **PM이 세션 종료 의무를 이행할 수 없는 구조적 모순**

**모순 2: 팀 스쿼드 운영 vs 호출 비효율**

- 설계 의도: PM이 Work Order 발행 → Doc Manager 작업 수행 (Haiku 비용 절감)
- 실제 운영: 디렉터가 수동으로 AI 도구 전환 (수작업 부담)
- 자동화 시도: Task 도구 → Sonnet 재투입 (비용 최적화 실패)

## 🚨 근본 원인 분석

### Session 19.5 감사의 설계 결함

**당시 권고:**
- PM 역할 과부하 및 경계 침범 → **권한 전면 제한**
- Documentation Manager 신설 → **문서 관리 전담**

**설계 의도:**
- 역할 경계 명확화
- PM의 오류 방지
- 비용 최적화 (Haiku 활용)

**간과한 점:**
- PM의 **세션 관리자** 역할 = 진척 추적/보고서 작성 = 문서 갱신 필수
- "금지"와 "제한"의 구분 없이 이분법적 설계
- 실제 운영 워크플로우 검증 부재

### 역할 복잡성 미고려

PM은 **단일 역할이 아닌 복합 역할**:

| 관점 | 역할 | 필요 권한 |
|:--|:--|:--|
| **조율자** | Work Order 발행, 팀 조율 | 읽기 + Work Order 생성 |
| **기록자** | 세션 보고, 진척 추적 | 04번 문서 갱신 |
| **감시자** | 공정 모니터링, 이슈 보고 | 읽기 + 이슈 기록 |

→ **"문서 수정 전면 금지"는 PM의 기록자 역할을 불가능하게 만듦**

단순한 "허용/금지"가 아닌 **작업 유형별 세분화된 권한 체계**로 전환합니다.

## 1단계: PM 권한 재정의 (계층적 접근)

### 허용 권한 (Tier 1: 세션 운영)

✅ **04_CURRENT_STATE.md 제한적 갱신**
- 허용: "완료 작업", "진행중", "이슈/차단사항" 섹션만
- 허용: 운영 스쿼드 "현재 작업" 상태 업데이트
- 금지: Phase 전환, 운영 스쿼드 역할/모델 변경, 구조 변경

✅ **세션 보고서 작성**
- 경로: `docs/reports/SESSION_XX_*.md`
- 자유 생성/수정 (PM 고유 영역)

✅ **Work Order 발행**
- 경로: `docs/work_orders/`
- 자유 생성/수정 (PM 고유 영역)

✅ **단순 파일 이동/정리**
- 아카이브: `docs/_archive/`로 이동
- 조건: 디렉터 승인 또는 기존 결정(D-019 등) 근거
- 금지: 삭제(Delete), 체계 변경

### 금지 권한 (변함없음)

❌ **정본 문서 구조 변경**
- `CLAUDE.md`, `01~03`, `05` 수정
- `04`의 Phase 전환, 운영 스쿼드 역할 변경

❌ **코드 직접 수정**
- `src/` 폴더 전체

❌ **콘텐츠 SSOT 수정**
- `docs/contents/` (Content 역할 영역)

❌ **문서 체계 변경**
- 신규 폴더 생성, 대규모 구조 개편

### 승인 필요 사항 (중간 지대)

⚠️ **03_DECISIONS.md 갱신**
- 허용: 디렉터가 세션 중 결정한 사항을 기록 (기록자 역할)
- 필수: 기록 전 디렉터에게 초안 확인 받기
- 금지: PM이 독단적으로 결정 기록 (결정 권한 없음)

⚠️ **05_NEXT_TASK.md 갱신**
- 허용: Work Order 근거 명시, 작업 상태 갱신
- 금지: 작업 지시 내용 변경 (Work Order와 불일치 방지)

## 2단계: Documentation Manager 역할 재정의

### 역할 재포지셔닝: **검증자 + 구조 전문가**

Documentation Manager는 **단순 반복 작업에서 해방**되어 **고부가가치 작업에 집중**합니다.

### 핵심 책임 (변경됨)

✅ **정합성 검증 (주 1회 또는 Phase 전환 시)**
- 정본 문서 간 모순 점검
- 콘텐츠 SSOT ↔ 코드 동기화 확인
- 링크 유효성 검사

✅ **문서 체계 변경 (설계/실행)**
- 신규 폴더 구조 제안
- 대규모 이동/리네임 실행
- 아카이브 정책 적용

✅ **마스터 문서 구조 변경**
- `CLAUDE.md`, `01~05`의 섹션 추가/삭제
- 버전 히스토리 관리
- 정본 문서 템플릿 개선

✅ **복잡한 문서 작업**
- 다수 문서에 걸친 일관성 유지
- 통합 보고서 작성 (예: Phase 완료 보고서)

### 호출 빈도 감소 (예상)

| 이전 (Session 19.5~19.6) | 개선 후 (Session 19.8+) |
|:--|:--|
| 매 세션 종료 시 호출 (04번 갱신) | Phase 전환 시만 호출 |
| 단순 파일 이동 (아카이브) | PM이 직접 처리 |
| 세션 보고서 검토 | PM 자체 완결 |
| **예상: 10회/10세션** | **예상: 2~3회/10세션 (70% 감소)** |

## 3단계: 세션 종료 프로토콜 재정의

### 개정된 프로토콜 (CLAUDE.md 섹션 5)

```markdown
## 5. 세션 종료 프로토콜 (Mandatory)

세션 종료 전 **반드시** 수행:

### 모든 역할 공통
1. **Git 상태 확인** — `git status`, `git diff` 결과 디렉터에게 보고
2. **세션 보고서 생성** — `docs/reports/SESSION_XX_[ROLE]_REPORT.md`

### PM 전용
3. **04_CURRENT_STATE.md 갱신** — 완료/진행중/이슈 섹션만 업데이트
4. **Work Order 상태 갱신** — 발행한 WO의 진척 상태 기록

### Documentation Manager 전용 (Phase 전환 시만)
5. **정본 문서 정합성 검증** — `01~05` 간 모순 점검
6. **버전 히스토리 갱신** — 구조 변경 시 마스터 문서 버전 업

### 코드 수정 역할 (Builder, Designer)
7. **빌드 확인** — `npm run build` 성공 확인
8. **Git 커밋 승인 요청** — 변경 내용 요약 + 디렉터 승인 대기
```

### 역할별 종료 체크리스트

| 역할 | 1-2 (공통) | 3-4 (PM) | 5-6 (Doc Mgr) | 7-8 (코드) |
|:--|:--:|:--:|:--:|:--:|
| PM | ✅ | ✅ | - | - |
| Documentation Manager | ✅ | - | ✅ | - |
| Builder | ✅ | - | - | ✅ |
| Content | ✅ | - | - | - |
| Designer | ✅ | - | - | - |
| Media Producer | ✅ | - | - | - |

## 🚨 리스크 관리

### 예상 리스크 및 완화 조치

**리스크 1: PM의 과도한 권한 사용**

- **시나리오:** PM이 04번 문서의 Phase 전환, 운영 스쿼드 변경 시도
- **완화 조치:**
  - 허용 범위를 **문서에 명시** ("완료/진행중/이슈 섹션만")
  - PM에게 명확한 가이드 제공 ("이 섹션만 수정 가능")
  - 디렉터가 Git diff 검토 시 범위 초과 확인

**리스크 2: 정본 문서 정합성 저하**

- **시나리오:** PM이 04번 갱신 시 실수로 모순 발생
- **완화 조치:**
  - Documentation Manager의 **주기적 검증** (Phase 전환 시)
  - PM의 변경 내역을 Git으로 추적
  - 디렉터 승인 과정에서 이상 징후 발견

**리스크 3: 역할 경계 모호화**

- **시나리오:** PM이 점진적으로 Doc Manager 영역 침범
- **완화 조치:**
  - RACI 매트릭스로 경계 명확화
  - 침범 발생 시 즉시 교정 (디렉터 피드백)
  - Phase 3 완료 후 전체 평가

Session 19.5에서 저는 **PM 통제 실패**를 이유로 **과도한 권한 제한**을 권고했습니다. 이는 **즉각적인 문제 해결**에는 효과적이었으나, **장기 운영 효율성**을 간과한 설계였습니다.

**교훈:**
- 역할 재편 시 **실제 워크플로우 검증** 필수
- "금지"가 아닌 **"제한적 허용"** 중심의 설계
- 이분법적 접근보다 **계층적 권한 체계**가 효과적

### 이번 개정안의 장점

1. **PM의 세션 관리자 역할 복원** (진척 추적 가능)
2. **Doc Manager의 전문성 집중** (고부가가치 작업)
3. **운영 효율성 70% 개선** (수동 전환 제거)
4. **리스크 관리 체계 유지** (주기적 검증, Git 추적)

### 우려 사항

1. PM의 권한 오남용 가능성 (완화: 명확한 범위 명시 + 디렉터 검토)
2. 점진적 역할 경계 모호화 (완화: RACI 매트릭스 + Phase별 평가)

### 최종 권고

**Session 19.8부터 개정안 적용을 권고합니다.**

- Phase 2 검증 단계에서 PM 오류율 30% 초과 시 즉시 롤백

- 다른 역할(Builder, Designer 등)도 유사한 계층적 권한 체계 적용 검토
