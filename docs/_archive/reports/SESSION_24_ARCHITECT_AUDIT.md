### 1.3 문제 유형 분류

#### 🔴 TYPE-A: HPOC 프레임워크 고객 노출 (17개 파일 전체)

디렉터 원문: *"HPOC 철학 같은 건 다 개소리다."*

**현상:** 거의 모든 페이지에 HPOC 프레임워크가 구조적으로 노출됨.

```
문제 예시:
- home.md: "## 2. 핵심 가치 제안 (HPOC 3축)"
- home.md: "### 2.1 Hardware (안전)" / "### 2.2 People (전문성)"
- service_corporate_training.md: "### 1.2 핵심 가치 (HPOC)"
- service_corporate_teambuilding.md: "### 1.2 핵심 가치 (HPOC)"
- (이하 모든 service 파일 동일 패턴)
```

**진단:** HPOC는 **내부 설계 도구**로서는 유효했다. 4축으로 메시지를 정리하는 데 도움이 됐다. 그러나 고객이 보는 웹사이트에 "Hardware", "People", "Operation", "Content" 라벨을 노출하는 것은 **컨설팅 보고서 톤**이지 웹사이트 톤이 아니다.

**수정 방향:** HPOC 라벨 제거, 메시지 내용은 유지하되 자연어로 재작성.
```
Before: "### 2.1 Hardware (안전)"
         "철저한 안전 대책과 프로그램 설계로..."

After:   "### 13년 무사고"
         "2013년 이래 418건의 행사, 단 한 건의 사고도 없었습니다."
```

**진단:** GPT가 설계한 브랜드 프레임워크의 언어가 Gemini 콘텐츠에 그대로 계승됐다. Gemini는 지시를 충실히 이행했으나, **지시 자체가 추상적 프레임워크 기반**이었기 때문에 결과물도 추상적이다. 이것은 Gemini의 잘못이 아니라 **WO 설계 시 톤 기준이 프레임워크(HPOC) 중심**이었던 구조적 문제다.

**수정 방향:** "무엇을 하는가"가 아니라 "고객이 어떤 경험을 하는가"로 관점 전환.
```
Before: "조직개발 전문가와 함께 설계된 체계적인 HRD 솔루션입니다."
After:  "삼성, 현대, LG 등 219개 기업이 선택한 팀빌딩입니다."

Before: "HRD 적용형 vs 비HRD 적용형"
After:  "연수 프로그램" vs "행사/이벤트"
```

## 2. 6가지 미해결 업무 검증

### 2.1 콘텐츠 정제 Work Order 재발행 (STEP 1-1)

**판정: 재발행 필수, 단 WO 구조 변경 권고**

기존 WO는 HPOC 프레임워크를 적용 기준으로 제시했는데, 그 프레임워크 자체가 문제의 원인이다. 새 WO는 다음을 반영해야 한다:

| 항목 | 기존 WO | 수정 권고 |
|:--|:--|:--|
| 톤 기준 | HPOC 4축 적용 | **디렉터 Home 샘플 톤 매칭** |
| 작업 방식 | AI 전체 생산 | **디렉터 샘플 → AI 톤 적용** |
| 금지 표현 | 과장/허위만 금지 | **추상어/컨설팅어/프레임워크 라벨 금지 추가** |
| 작업자 | Gemini 3.0 Pro | **Opus 4.6 권고** (톤 뉘앙스 민감도 필요) |

---

### 2.2 CEO 콘텐츠 기준 정화 방식

**3가지 옵션 비교:**

| 옵션 | 방식 | 장점 | 단점 | 소요 시간 |
|:--|:--|:--|:--|:--|
| **A (권고)** | 디렉터가 Home 1페이지 직접 작성 → Opus가 나머지 16개 톤 매칭 | 디렉터 의도 100% 반영 + AI 확장 가능 | 디렉터 Home 작성 시간 필요 | 디렉터 1~2h + Opus 2~3h |
| B | 디렉터가 "금지 표현 리스트"만 제공 → Opus가 전체 17개 재작성 | 디렉터 부담 최소 | 톤 방향성 불명확, 반복 수정 가능 | 디렉터 30min + Opus 3~4h + 수정 반복 |
| C | 디렉터가 17개 전부 직접 수정 | 완벽한 통제 | 비현실적 소요 시간 | 디렉터 8~12h |

**권고:** 옵션 A. 디렉터가 Home만 직접 작성하면 "이게 내가 원하는 톤이다"라는 명확한 기준점이 생긴다. Opus는 그 톤을 분석하여 나머지 16개에 적용한다. Home은 브랜드 첫인상이므로 디렉터가 직접 쓰는 것이 가장 효과적이다.

**Home 샘플 작성 가이드 (디렉터용):**
1. 현재 `home.md`를 열고 원하는 톤으로 자유롭게 수정
2. HPOC 라벨 / 추상어 / 컨설팅 용어는 빼고, "고객한테 직접 말하듯" 작성
3. 완성되면 "이 톤이 기준이다"라고 선언
4. Opus가 나머지 16개를 동일 톤으로 재작성

---

### 2.3 나머지 16개 파일 처리 (CEO 직접 vs Opus)

**판정: Opus 일괄 처리 + 디렉터 핵심 4개 검수**

- 디렉터 직접: Home 1개 (톤 기준점)
- Opus 재작성: About, Programs, Corporate Hub, Service Hub (핵심 4개 우선)
- 디렉터 2차 검수: 핵심 4개 승인
- Opus 잔여 처리: 나머지 12개 (핵심 4개 톤 따라 기계적 적용)
- 디렉터 최종 검수: 전체 17개 스캔

**근거:** Gemini가 만든 구조/데이터/CTA는 양호하므로, Opus는 "표현 교체"만 수행. 전면 재작성이 아니라 **톤 리라이팅**이다.

---

### 2.4 STEP 2/3 일정 재계획

**현실적 의존 관계:**

```
STEP 1-1 (톤 리라이팅)
  └─ 디렉터 Home 샘플 [선행]
     └─ Opus 핵심 4개 재작성 [2차]
        └─ 디렉터 검수 [3차]
           └─ Opus 나머지 12개 [4차]
              └─ 디렉터 최종 검수 [5차]
                 └─ STEP 2 착수 가능

STEP 2 (미디어 자산)
  └─ 콘텐츠 확정 후 (STEP 1-1 완료)
     └─ Gemini Flash 이미지 생산 [1~2일]

STEP 3 (디자인 폴리싱)
  └─ STEP 1-1 + STEP 2 완료 후
     └─ Builder/Designer 코드 바인딩 [2~3일]
```

**부분 병렬화 가능 구간:**
- STEP 2는 Home + About + Programs 콘텐츠 확정 시점에 해당 3개 페이지부터 착수 가능
- History 페이지는 톤 변경 영향이 적으므로 STEP 2와 병렬 진행 가능

### 3.3 PM 개선안

#### 즉시 적용 (다음 세션부터)

**PM 파일 조회 체크리스트:**

```
□ 1. 대상 폴더 전체 열거: ls 또는 Glob(**/*) 먼저 실행
□ 2. 총 파일 수 확인: "이 폴더에 N개 파일 존재" 명시
□ 3. 각 파일 목적 1줄 요약: 파일명 → 역할 매핑
□ 4. 누락 가능성 점검: "N개 중 M개 읽음, 누락 없음" 또는 "K개 미확인"
□ 5. 보고 시 파일 리스트 첨부: 디렉터가 직접 확인 가능하도록
```

**PM 보고 품질 체크리스트:**

```
□ 1. "완료"/"전수"/"전체" 단어 사용 전: 실제 전수 확인했는가?
□ 2. 패턴 검색 결과를 "전체"라고 보고하지 않는다
□ 3. 불확실한 경우 "N개 확인, 추가 파일 존재 가능" 표현 사용
□ 4. 디렉터에게 보고 전 자기 검증 1회 수행
```

#### 시스템 개선 (Doc Manager 협업)

- **네이밍 규칙 강화**: 이슈별 폴더 내 파일은 `[이슈ID]_[순번]_[내용].md` 형식 통일
- **최종 결정 문서 표준**: 이슈 종결 시 반드시 `[Final_Decision]_` 접두어 사용하고, README 또는 INDEX 파일로 폴더 내 파일 목록 관리
